From JuMP to PowerSimulations.jl ​

In the previous section, we wrote the dispatch of a toy market as one JuMP model. PowerSimulations.jl (PSI) is the framework this repository builds its NEMDE replica on. This page introduces its concepts by rebuilding the energy-only part of the toy market.

PSI splits a model into three layers of abstraction:

LayerAnswersPackage and objectOn this page
DataWhat is the market?PowerSystems.jl (PSY): a System of components and time seriesregions, units, offers, demand, the interconnector
FormulationHow is one kind of component modelled?PSI: a formulation type, with methods that write its variables, constraints and costs"a scheduled unit is dispatched between bounds at its offer cost"
ProblemWhich formulation applies to which component, over which horizon?PSI: a ProblemTemplate and a DecisionModelone 5-minute dispatch interval

When using PSI, no line of the JuMP model is written by hand: PSI leverages Julia's multiple dispatch on the pair (component type, formulation type) to build the JuMP model.

Units and their offers ​

A unit's energy offer is its variable cost: a PiecewiseIncrementalCurve whose x-coordinates are the cumulative band quantities and whose slopes are the band prices, the bid stack of the JuMP model. The offer of COAL1, read back from the System:

The dispatch envelope of the JuMP model (availability, and the ramp from INITIALMW over one interval) has no direct field here: PSI's stock formulations ramp between consecutive time steps of the problem, not from a metered initial output. For a single interval the envelope is a pair of bounds, so it is stored in active_power_limits (and rating for the renewable unit).

Demand as a time series ​

A component field is a constant. Anything that changes from one interval to the next (demand, a forecast, a bid) is a time series attached to a component. PSI reads it into the model as a parameter, so the same built model can be re-solved for the next interval by updating parameter values instead of rebuilding. Here the series is a multiplier on max_active_power.

PSI solves over forecast windows, so the single series is turned into windows of two intervals that advance by one: the shortest window PSI accepts. toy_system applies this transform to each load.

Nothing in the System says how a unit is dispatched or what a region's balance looks like. That is the job of the next two layers.

Mapping the abstractions ​

Before going into PSI.jl, let's first build the intuition behind the abstractions it develops. Let's look again at the complete JuMP model from the previous section, reordering some of the function calls. It still includes the FCAS service, the interconnector losses and the generic constraints, which the PSI model of this page leaves out; the grouping is what matters here.

julia
function build_model(sys, market)
    model = Model(HiGHS.Optimizer)
    set_silent(model)
    ic = market.interconnector
    segments = linearised_losses(ic)
    n_segments = length(segments)
    names = generator_names(sys)
    bands = Dict(n => offer_bids(sys, n) for n in names)
    envelopes = Dict(n => envelope(sys, n) for n in names)
    fnames = fcas_names(market)
    regions = region_names(sys)
    from = PSY.get_name(PSY.get_from_area(interconnector(sys)))

    # Define Arguments: variables and expressions specific to:
    # 1.1. Devices:
    # 1.1.1. Units
    @variable(model, 0 <= cleared[n in names, j in eachindex(bands[n])] <= quantity(bands[n][j]))
    @expression(model, dispatch[n in names], sum(cleared[n, j] for j in eachindex(bands[n])))
    @expression(model, offer_cost, sum(price(bands[n][j]) * cleared[n, j] * INTERVAL_H for n in names for j in eachindex(bands[n])))
    # 1.1.2 Interconnectors
    @variable(model, flow)
    @variable(model, 0 <= segment_flow[s in 1:n_segments] <= segments[s].to_mw - segments[s].from_mw)
    @variable(model, filled[s in 1:(n_segments - 1)], Bin)
    @expression(model, loss, loss_at(ic, ic.breakpoints[1]) - zero_flow_chord_loss(ic) + sum(segments[s].slope * segment_flow[s] for s in 1:n_segments))
    # 1.2 Services
    # 1.2.1 FCAS
    @variable(model, 0 <= raise[n in fnames] <= max_avail(trapezium(market, n)))
    @variable(model, 0 <= raise_cleared[n in fnames, j in eachindex(fcas_bids(market, n))] <= quantity(fcas_bids(market, n)[j]))
    @expression(model, fcas_cost, sum(price(b) * raise_cleared[n, j] * INTERVAL_H for n in fnames for (j, b) in enumerate(fcas_bids(market, n))))


    # Define Constraints. Constraints must be defined after their variables and coefficients / parameters are defined.
    # 2.1 Devices
    # 2.1.1 Units
    @constraint(model, envelope_min[n in names], dispatch[n] >= envelopes[n][1])
    @constraint(model, envelope_max[n in names], dispatch[n] <= envelopes[n][2])
    # 2.1.2 Interconnectors
    @constraint(model, flow_definition, flow == ic.breakpoints[1] + sum(segment_flow))
    @constraint(model, segment_full[s in 1:(n_segments - 1)], segment_flow[s] >= (segments[s].to_mw - segments[s].from_mw) * filled[s])
    @constraint(model, segment_next[s in 1:(n_segments - 1)], segment_flow[s + 1] <= (segments[s + 1].to_mw - segments[s + 1].from_mw) * filled[s])
    @constraint(model, flow_limit_up, flow <= flow_limit(sys))
    @constraint(model, flow_limit_down, flow >= -flow_limit(sys))

    # 2.2 Services
    # 2.2.1 FCAS Constraints
    @constraint(model, raise_definition[n in fnames], raise[n] == sum(raise_cleared[n, j] for j in eachindex(fcas_bids(market, n))))
    @constraint(model, trapezium_upper[n in fnames], dispatch[n] + upper_slope(trapezium(market, n)) * raise[n] <= trapezium(market, n).enablement_max)
    @constraint(model, trapezium_lower[n in fnames], dispatch[n] - lower_slope(trapezium(market, n)) * raise[n] >= trapezium(market, n).enablement_min)


    # 2.3 Joint devices constraints
    generation(r) = sum(dispatch[n] for n in units_in(sys, r))
    exported(r) = r == from ? flow : -flow
    loss_charged(r) = (r == from ? ic.from_loss_share : 1 - ic.from_loss_share) * loss
    @constraint(model, balance[r in regions], generation(r) - exported(r) - loss_charged(r) == region_demand(sys, r))

    function term_variable(t::Term)
        t.kind == :energy && return dispatch[String(t.id)]
        t.kind == :raise6 && return raise[String(t.id)]
        return flow
    end

    generic = Dict{String, ConstraintRef}()
    violation = Dict{String, VariableRef}()
    violation_cost = AffExpr(0.0)
    for gc in market.constraints
        lhs = sum(t.factor * term_variable(t) for t in gc.terms)
        v = @variable(model, lower_bound = 0, base_name = "violation_$(gc.name)")
        generic[gc.name] = if gc.sense == :LE
            @constraint(model, lhs - v <= gc.rhs)
        else
            @constraint(model, lhs + v >= gc.rhs)
        end
        violation[gc.name] = v
        add_to_expression!(violation_cost, gc.weight * MARKET_PRICE_CAP * INTERVAL_H, v)
    end
    model[:generic] = generic
    model[:violation] = violation

    @objective(model, Min, offer_cost + fcas_cost + violation_cost)
    return model
end

The grouping above surfaces the main building phases of a model, independently of the concrete data:

  1. Initialise empty containers to hold expressions spanning devices and services. These are used later to build constraints.

  2. Attach the variables and parameters of each system component: devices, services, branches.

  3. Attach the constraints:

    1. for each device, service and branch, the constraints indexed only on itself;

    2. the contribution of each device, service and branch to the expression containers of step 0, where applicable;

    3. the constraints written on those expression containers.

  4. Attach the objective function to the model.

The problem: a template and a decision model ​

A ProblemTemplate pairs each component type with a formulation, and fixes the network model: how the components' injections are balanced. AreaBalancePowerModel writes one balance row per Area, with AreaInterchange flows moving power between areas. With one area per region, that is the NEM's regional market.

A DecisionModel adds what the template leaves open: the data and solver, the first interval and the horizon. Building: how PSI writes the JuMP model ​

build! runs the construction phases below in a fixed order, handing the same container to each. Devices, services and branches are each visited twice. The argument stage adds variables, parameters and expressions. The model stage adds the constraints and costs on them. The split lets every component contribute to a shared expression, such as a region's balance, before any constraint is written on it.

Let's see how this translates into PSI directly.

julia
function build_impl!(model::DecisionModel{<:DecisionProblem})
    build_pre_step!(model)
    @info "Instantiating Network Model"
    instantiate_network_model!(model)
    handle_initial_conditions!(model)
    build_model!(model)
    serialize_metadata!(get_optimization_container(model), get_output_dir(model))
    log_values(get_settings(model))
    return
end

# PowerSimulations.jl/src/core/optimization_container.jl
function build_impl!(
    container::OptimizationContainer,
    template::ProblemTemplate,
    sys::PSY.System,
)
    transmission = get_network_formulation(template)
    transmission_model = get_network_model(template)
    hvdc_model = get_hvdc_network_model(template)

    # Expression containers spanning devices/branches/units
    # Contributing components will add their contribution to the expression
    initialize_system_expressions!(
        container,
        get_network_model(template),
        transmission_model.subnetworks,
        get_branch_models(template),
        sys,
        transmission_model.network_reduction.bus_reduction_map
    )

    ...

    # Order is required
    for device_model in values(template.devices)
        # Attach device specific variables and expressions
        construct_device!(
            container,
            sys,
            ArgumentConstructStage(),
            device_model,
            transmission_model,
        )
    end

    # Attach service specific variables and expressions
    construct_services!(
        container,
        sys,
        ArgumentConstructStage(),
        get_service_models(template),
        get_device_models(template),
        transmission_model,
    )

    for branch_model in values(template.branches)
        # Attach branch specific variables and expressions
        construct_device!(
            container,
            sys,
            ArgumentConstructStage(),
            branch_model,
            transmission_model,
        )
    end

    # Now we attach the constraints

    for device_model in values(template.devices)
        # Device specific constraints + expression contributions
        construct_device!(
            container,
            sys,
            ModelConstructStage(),
            device_model,
            transmission_model,
        )
    end

    # This function should be called after construct_device ModelConstructStage
    construct_network!(container, sys, transmission_model, template)
    construct_hvdc_network!(container, sys, transmission_model, hvdc_model, template)

    for branch_model in values(template.branches)
        # branch specific constraints + expression contributions
        construct_device!(
            container,
            sys,
            ModelConstructStage(),
            branch_model,
            transmission_model,
        )
    end

    # Service specific constraints + expression contributions
    construct_services!(
        container,
        sys,
        ModelConstructStage(),
        get_service_models(template),
        get_device_models(template),
        transmission_model,
    )


    # Objective function
    update_objective_function!(container)

    ...

    check_optimization_container(container)
    return
end

Each phase is shown below next to the lines of the JuMP model it replaces. Highlighted lines are the ones the phase generates.

Phase 0 and 1: variables and the balance terms ​

In the JuMP model each unit's dispatch is declared, then each region's balance sums the dispatch of its units. In PSI the balance is an ActivePowerBalance expression per area, created empty in phase 0. In phase 1 each unit declares its variables and adds its own power to the expression of its area, and each load subtracts its demand parameter. A device never sees the balance row, so a new device type needs no change to it.

julia
@variable(model, 0 <= cleared[u in units(market), j in 1:n_bids(u)] <= quantity(bid(u, j)))  
@expression(model, dispatch[u in units(market)], sum(cleared[u, j] for j in 1:n_bids(u)))  
generation(r) = sum(dispatch[u] for u in units_in(market, r))

The argument-stage method is a list of calls, each adding one kind of object to the container. This is the method this repository writes for its NEM dispatch formulations, abridged:

julia
function PSI.construct_device!(
        container, sys, ::PSI.ArgumentConstructStage,
        model::PSI.DeviceModel{T, D}, network_model,
    ) where {T <: PSY.StaticInjection, D <: AbstractNEMDispatch}
    devices = PSI.get_available_components(model, sys)
    PSI.add_variables!(container, PSI.ActivePowerVariable, devices, D())  
    PSI.add_parameters!(container, InitialPowerTimeSeriesParameter, devices, model)
    PSI.add_cost_expressions!(container, devices, model)
    PSI.add_to_expression!(  
        container, PSI.ActivePowerBalance, PSI.ActivePowerVariable, devices, model, network_model,
    )
    return
end

The where clause is the dispatch rule: the method runs for any component type T modelled with any formulation D under AbstractNEMDispatch.

Phase 3: the interconnector flow ​

The flow is a variable of the branch, declared in the branches' argument stage and added to the two area balances with opposite signs:

julia
@variable(model, flow)  
exported(r) = r == ic.from ? flow : -flow

Phase 4: component constraints and costs ​

Rows that involve one component: in the JuMP model, availability and the ramp envelope. Here they are the limits of ActivePowerVariable read from active_power_limits. The offer cost is registered with the container rather than written into an objective.

julia
@constraint(model, availability_limit[u in units(market)], dispatch[u] <= availability(u))  
@constraint(model, ramp_up_limit[u in units(market)], dispatch[u] - initial_mw(u) <= ramp_up(u))  
@constraint(model, ramp_down_limit[u in units(market)], initial_mw(u) - dispatch[u] <= ramp_down(u))

The model-stage method of the NEM formulation writes these rows from per-interval parameters, with the ramp measured from the metered initial output (abridged):

julia
function PSI.construct_device!(
        container, sys, ::PSI.ModelConstructStage,
        model::PSI.DeviceModel{T, D}, network_model,
    ) where {T <: PSY.StaticInjection, D <: AbstractNEMDispatch}
    devices = PSI.get_available_components(model, sys)
    _add_energy_limit_rows!(container, EnergyLimitMaxAvailVariant(), PSI.ActivePowerVariable, devices, model, network_model)  
    PSI.add_constraints!(container, PSI.RampConstraint, PSI.ActivePowerVariable, devices, model, network_model)  
    PSI.objective_function!(container, devices, model, PSI.get_network_formulation(network_model))  
    return
end

The energy-limit rows are built by the formulation's helper _add_energy_limit_rows!, dispatched on the variant tag, and the fixed-load rows by add_constraints! on NEMUnitConstraint. The PSI.RampConstraint call is dispatched on the formulation, so a NEM formulation runs this repository's ramp rows while a stock formulation runs PSI's.

Phase 5: the network ​

The constraint joining components: each area's balance expression, now complete with every device and branch term, is set equal to zero. Demand entered it in phase 1 as a negative term from each PowerLoad. The dual of this row is the regional price.

julia
@constraint(  
    model, balance[r in market.regions],  
    generation(r) - exported(r) - loss_charged(r) == region_demand(market, r),  
)

Phase 6 and 7: branch limits and services ​

Flow limits are model-stage constraints of the branch. Services are PSI's objects for requirements shared by a group of devices, such as a reserve. Their constraints act on variables of several devices, and sometimes on flows, so they are written last. In the JuMP model the FCAS rows and the generic constraints play this role; in the next page they are services.

julia
@constraint(model, flow_limit_up, flow <= ic.max_flow)  
@constraint(model, flow_limit_down, flow >= -ic.max_flow)  
@constraint(model, trapezium_upper[u in fcas_units(market)], dispatch[u] + upper_slope(trapezium(u)) * raise[u] <= trapezium(u).enablement_max)  
add_generic_constraint!(model, gc)

Phase 8: the objective ​

Every phase registers its cost terms (offers, slacks, penalties) in the container instead of writing an objective. update_objective_function! sums them once, at the end:

julia
@objective(model, Min, offer_cost)  
set_objective_function(model, objective_function(model) + fcas_cost)

The container: where the model lives ​

The OptimizationContainer is a typed registry of everything the phases added. An entry is addressed by a key (entry type, component type) instead of a variable name:

julia
container = PSI.get_optimization_container(model_psi)

function container_keys(container)
    rows = NamedTuple{(:kind, :entry, :component, :meta), NTuple{4, String}}[]
    for (kind, entries) in (
            "variable" => PSI.get_variables(container),
            "expression" => PSI.get_expressions(container),
            "parameter" => PSI.get_parameters(container),
            "constraint" => PSI.get_constraints(container),
        )
        for key in keys(entries)
            push!(
                rows,
                (;
                    kind, entry = string(nameof(PSI.IS.Optimization.get_entry_type(key))),
                    component = string(nameof(PSI.IS.Optimization.get_component_type(key))),
                    key.meta,
                ),
            )
        end
    end
    return sort!(DataFrame(rows), [:kind, :entry])
end

Three differences from the JuMP model show in the printout:

  • Values are per unit of the system base: NSW1's 450 MW of demand is 4.5.

  • The offer is written as weights on the breakpoints of the cost curve (PiecewiseLinearCostVariable, summing to 1), not as MW per band. For an offer whose prices rise with quantity the two give the same dispatch and cost. WIND1 offers only at $0, so it adds no cost variables.

  • Demand, a parameter, appears as the right-hand side of each balance row.

Solving and reading results ​

Results are read back by the same keys, written as "Entry__Component". Variables are in MW. Duals are per unit of the system base and per interval, so dual / (BASE_POWER * interval hours) is $/MWh.

julia
solve_status = PSI.solve!(model_psi)
results = PSI.OptimizationProblemResults(model_psi)

psi_dispatch = Dict(
    Symbol(r.name) => r.value
        for key in ("ThermalStandard", "RenewableDispatch")
        for r in eachrow(PSI.read_variable(results, "ActivePowerVariable__$key"))
)
psi_price = Dict(
    r.name => r.value / (BASE_POWER * INTERVAL_H)
        for r in eachrow(PSI.read_dual(results, "CopperPlateBalanceConstraint__Area"))
)
psi_flow = only(
    PSI.read_variable(results, "FlowActivePowerVariable__AreaInterchange").value,
);
